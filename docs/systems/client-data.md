# 클라이언트 데이터 관리

서버 데이터의 원본은 서버이며, 공유 캐시는 TanStack Query가 관리한다. 기존 Context는 화면에 필요한 값과 효과를 제공하는 인터페이스로 유지한다. 인증 세션은 Supabase Auth가 관리하고 Zustand에는 도감 필터처럼 화면 사이에서 공유할 UI 선호만 넣는다. 잔액·경험치·보유량을 Zustand나 영구 브라우저 저장소에 복제하지 않는다.

계정 데이터 키는 계정 ID를 포함해야 한다. Auth가 세션을 React에 전달하기 전에 이전 계정 요청을 취소하고 캐시를 제거한다. 거래 시작 시 캡처한 계정 범위가 바뀌면 늦게 도착한 응답으로 캐시를 채우지 않는다. 읽기 함수는 Query의 AbortSignal을 Supabase 요청에 전달한다.

조회는 화면의 query observer와 기존 명령형 로더가 같은 키를 사용한다. 같은 시점의 요청은 공유하고, 짧은 화면 재진입은 유효한 캐시를 사용한다. 서버 시각을 포함한 캐시를 명령형 화면에 전달할 때는 경과 시간을 반영해 카운트다운이 다시 시작되지 않게 한다. 메뉴는 상세 카탈로그·지난 기록·지갑 초기화를 호출하지 않는 요약 RPC를 공유한다. 완료·만료 표시는 알려진 기한에서 로컬로 갱신한다. 새 화면의 주기적 조회는 앱 루트의 공통 타이머에 맡긴다. 기존 화면에 남은 자체 폴링은 해당 화면을 query observer로 전환할 때 함께 제거한다.

쓰기 요청은 자동 재시도하지 않는다. 기존 거래의 operation ID 유지 및 결과가 불확실할 때 같은 ID로 확인하는 절차를 보존한다. 전체 상태가 포함된 성공 응답은 캐시에 바로 반영하고 해당 도메인을 재조회하지 않는다. 완전한 상태가 없는 다른 도메인은 변경 이벤트로 무효화한다. 금액이나 경험치를 서버 확인 전에 증가시키지 않는다.

알림 목록과 배지 수는 같은 RPC 스냅샷으로 받는다. 알림 목록의 표시 제한을 전체 읽지 않은 수에 적용하지 않으며, 선물 배지는 알림 읽음 여부와 별도로 수령 대기 선물을 포함한다. 공지 공개 여부와 친구 요청 참가자 권한은 기존 RLS를 그대로 적용한다. Realtime은 기존 계정 범위 구독을 유지하며 캐시와 화면 상태를 함께 갱신한다.

새 기능을 옮길 때는 중복 로컬 상태와 기존 갱신 리스너를 함께 검토한다. 서버 데이터 키에 필터나 페이지가 영향을 주면 키에도 포함한다. 호출 수 검증과 함께 계정 전환, 늦은 응답, 이벤트 유실, 거래 중복 방지를 확인한다. 캐시 단위 테스트의 호출 감소를 실제 운영 전체 요청량 감소율로 표현하지 않는다.

## 새 기능과 기존 기능 변경 절차

1. 먼저 상태의 소유자를 정한다. 서버에서 받은 상태는 Query, 여러 화면에서 공유할 필터·정렬은 Zustand, 다이얼로그·선택·애니메이션·진행 중 작업 잠금은 React가 소유한다. 작은 기능마다 새 전역 store를 만들지 않는다. Context는 기존 소비자 인터페이스가 필요할 때 유지한다.
2. 읽기는 기능 API 모듈에 둔다. `readX(signal: AbortSignal)`에서 `.abortSignal(signal)`을 전달하고 화면에서는 `useAccountResource`로 관찰한다. 명령형 호출이 필요한 경우 `loadX`가 같은 키로 `readAccountResource`를 호출한다. Query의 queryFn 안에서 같은 키의 `loadX`를 호출하지 않는다.
3. 키는 `accountQueryKey`를 통해 구성한다. 자원 이름 뒤에 응답에 영향을 주는 페이지·검색어·필터·방문 대상 등을 모두 넣는다. 예를 들어 `['storage', offset, query, kind, rarity, concept]`는 보관함 API의 실제 키 형태다. 자원 이름으로 무효화하면 모든 페이지·필터가 함께 오래된 상태로 표시된다. 강제 재확인이 필요한 가격·상태 충돌 복구는 `readAccountResource`의 `{fresh:true}` 또는 observer의 `refetch`를 사용한다.
4. 쓰기는 `accountCommand`에서 한 번만 실행한다. 응답이 조회와 같은 완전한 상태일 때만 `resource`로 게시한다. 일부 개체만 반환하는 배치·크기 조정은 전체 스냅샷으로 게시하지 않는다. 해당 화면은 `useAccountState`로 확인된 부분 응답을 공통 캐시에 패치하거나 관련 자원을 무효화한다. 이 adapter는 별도의 서버 상태 사본을 만들지 않으며, 패치 전 진행 중인 읽기를 취소한다.
5. 변경이 영향을 주는 다른 자원을 명시한다. 공통 이벤트의 의존성은 `account-cache.ts`에서 관리하고, 개별 명령에만 필요한 것은 `invalidate`로 지정한다. 공통 명령이 이미 처리한 이벤트를 화면에서 다시 발행하지 않는다. 소리·경험치 알림 등 부수 효과는 `after`에서 실행하면 계정 범위 검사 뒤에만 실행된다.
6. 기존 operation ID의 생성·보관·확정 실패와 통신 실패 구분을 보존한다. 공통 명령은 ID를 생성하거나 자동 재시도하지 않는다. 계정 전환 오류는 서버 롤백을 뜻하지 않는다. 이전 계정에서 성공했을 수 있으므로 새 계정으로 재전송하지 않는다.

`useAccountState`의 계정 없는 독립 실행은 개발 화면·단위 테스트용이다. 운영에서는 로그인한 계정의 키만 활성화한다. query observer로 이전한 화면은 자체 초기 조회, focus/online 리스너, 같은 자원을 복제하는 `useState`를 함께 정리한다. 시계 표시용 로컬 tick과 서버 폴링은 구분한다.

## 자동 검사와 남은 이전 작업

`npm run client-data:check`는 TypeScript AST로 새 RPC가 화면에 직접 추가되거나 공통 조회·명령 경계를 우회하는지 검사한다. 공통 읽기 경로에서는 RPC 체인의 AbortSignal 전달도 확인한다. `npm run test:client-data`는 계정 경계·관련 화면 회귀를 확인한다. `.github/workflows/client-data.yml`에서 두 검사와 전체 빌드를 실행한다.

기존 예외는 `scripts/client-data-legacy.json`의 코드 지문으로 제한한다. 이 파일은 기존 코드에서 생성한 이전 작업 기준이며, 권장 API 목록이나 적용 완료 목록이 아니다. 예외 함수의 동작을 변경하면 검사에 실패하므로 해당 함수를 공통 경계로 옮긴다. 이전을 끝낸 항목은 목록에서 제거하고 새 항목을 추가하거나 지문을 교체해 통과시키지 않는다. 공백·주석 변경은 예외 동작 변경으로 취급하지 않는다.

남은 자체 폴링·로컬 서버 상태는 관련 기능을 수정할 때 observer로 옮긴다. 거래소·낚시처럼 준비·확정 단계가 있거나 호출 자체가 상태를 변경하는 RPC는 이름만 보고 읽기 캐시에 넣지 않는다. 먼저 명령 경계와 기존 operation ID 절차를 확인한다. 새 Zustand store를 도입할 이유는 여러 화면이 공유하는 UI 상태가 있을 때이며 서버 캐시를 옮기기 위해 추가하지 않는다.

정적 검사는 키에 모든 필터가 들어갔는지, 응답이 완전한 상태인지, RLS가 올바른지까지 증명하지 않는다. `.from()` 조회와 Realtime도 별도로 검토한다. 관련 변경에서는 요청 공유, A→B→A 계정 전환 후 늦은 응답, 성공 후 갱신, 실패 시 동일 작업 확인, 페이지·필터별 분리를 회귀 테스트로 확인하고 `npm run build`를 실행한다. DB 계약을 변경할 때의 원격 조회·migration 검증은 [DB 관리](database-management.md)를 따른다.
