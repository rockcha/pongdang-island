# 거래소와 물품 보관

상인거리 → 거래소(`/merchant-street/exchange`)에서 개체·미끼 판매 글을 등록합니다. 판매 목록·내 판매 분류와 물품 이름 검색, 20개 단위 페이지 이동을 제공합니다. 기존 상인거리 배너와 크림·갈색 공통 UI를 사용합니다.

## 교환 규칙

판매 등록은 이름 검색 → 보유 물품 결과에서 선택 → 판매 수량·골드 가격 입력 순서입니다. 드롭다운은 사용하지 않으며 검색 결과에 이미지·이름·보유 수량을 표시합니다. 검색어를 바꿔도 이미 선택한 물품과 입력한 수량은 유지하고, 다른 물품을 선택하면 수량을 1로 시작합니다.

거래 목록은 이미지·이름·수량·판매자와 오른쪽 가격·구매 버튼으로 구성한 구분선 행을 사용합니다. 등록 모달은 최대 폭 420px, 높이 `min(640px, 100dvh - 2rem)`으로 고정합니다. 검색 결과만 내부 스크롤하고 선택한 물품·수량·전체 가격·등록 버튼은 하단에 고정합니다. 로딩·빈 검색·검색 결과 없음·오류에도 공간을 유지합니다. 아주 낮은 화면에서는 뷰포트에 맞춰 전체 높이가 줄어듭니다.

- 개체나 미끼 한 종류를 맡기고 전체 수량에 대한 골드 가격을 지정합니다. 삽니다·물물교환·골드 판매는 지원하지 않습니다.
- 친구가 아니어도 로그인한 누구나 정해진 골드를 지불하고 구매할 수 있습니다. 자기 글은 구매할 수 없습니다.
- 어종·장식물·쓰레기를 지원합니다. 지도·낚싯대·클라이언트 테스트 개체는 거래하지 않습니다. 개체는 창고에 있는 것만 선택하며 전시 중인 개체는 먼저 창고로 옮깁니다.
- 상품은 한 종류와 수량으로 구성합니다. 개체 1~20개, 미끼 1~9,999개, 골드 1~1,000,000,000 범위입니다. 가격은 묶음 전체 기준입니다.
- 수수료·만료·가격 협상·부분 교환은 없습니다. 계정당 활성 글은 최대 10개입니다.
- 게시 즉시 미끼를 차감하거나 개체를 선물 보관 상태로 바꿉니다. 창고·전시·판매·재선물 대상에서 제외합니다.
- 구매자가 골드를 지불하면 상품은 구매자, 골드 대금은 판매자의 우편함 선물 탭으로 배송하고 각각 구매 완료·판매 성사 알림을 보냅니다. 개체는 기존 UUID를 유지하고 새 개체를 복제하지 않습니다.
- 작성자는 교환 전까지 취소할 수 있습니다. 맡긴 물품은 우편함으로 반환하며 직접 지갑·창고에 넣지 않습니다.
- 수령 시 골드는 지갑, 미끼는 기존 inventory, 개체는 창고로 들어갑니다. 보유 한도 초과 시 우편을 미수령으로 보존합니다. 수령한 개체는 도감 발견에도 기록합니다.

## 데이터·권한

`exchange_listings`는 작성자·판매 상품/골드 가격 스냅샷·상태·구매자·작업 UUID·보관 선물 ID를 저장합니다. RLS로 활성 글은 인증 사용자에게, 종료 글은 당사자에게만 공개하며 직접 쓰기는 차단합니다. 내 판매 화면은 내가 게시한 글의 상태와 기록을 보여줍니다. 교환해서 받은 물품은 우편함에서 확인합니다.

기존 `collectible_gifts`에 source·exchange_hold·reward_kind·reward_id를 추가합니다. 보관 중인 self 선물은 거래소 내부용으로만 사용하고 SELECT 정책·선물 목록·상세·수령에서 차단합니다. 교환/취소 후 보관 플래그를 해제하고 기존 선물 도착 알림을 생성합니다. 친구 선물의 최대 20개 제한·친구 검사·메모·이모지 흐름은 유지합니다. 거래 선물 화면에는 이모지 답장을 표시하지 않습니다.

공개 RPC는 INVOKER이며 비공개 구현은 auth.uid()를 검사하는 DEFINER·빈 search_path를 사용합니다. 브라우저는 물품 종류·ID·수량만 보내며 이름·이미지·가격 설명과 보유 개체 선택은 서버에서 확정합니다. 실제 개체 선택은 UUID 순서로 잠그고 전시/판매/선물 상태를 재검사합니다. 내부 물품 보관·배송 도우미는 인증 역할도 직접 실행할 수 없습니다.

변경은 지갑 → 거래 글 → 보관 개체 순서로 잠급니다. 교환 양쪽 지갑은 UUID 순서로 잠가 서로 반대 방향 거래의 잠금 순서도 맞춥니다. 등록은 작성자+작업 UUID로 중복 차감을 막고 같은 UUID의 조건 변경은 거부합니다. 교환·취소·수령은 최종 상태를 확인해 재시도를 중복 지급 없이 처리합니다. 게시·교환·취소와 배송 알림은 각각 한 트랜잭션이며 일부 실패하면 전부 취소됩니다. 클라이언트는 처리 중 중복 클릭을 막고 통신 오류 시 등록 작업 UUID를 유지합니다.

## 판매 전용 전환

[20261016164527_exchange_sales_only.sql](../../supabase/migrations/20261016164527_exchange_sales_only.sql)이 판매 전용 규칙을 적용합니다. 기존 활성 삽니다·물물교환 글은 취소하고 맡긴 물품을 우편으로 반환하며, 유효한 골드 판매 글과 종료 기록은 보존합니다. 이전 규칙의 글은 DB 기록으로만 보존하고 판매 목록에서 제외합니다. 이전 거래소 SQL을 이미 적용했다면 이 전환 SQL만 추가 실행합니다. 처음 설치한다면 아래 초기 SQL과 전환 SQL을 순서대로 실행합니다. 원격 실행 여부는 확인하지 않았습니다.

## 적용과 검증

[20261016162605_exchange_escrow_market.sql](../../supabase/migrations/20261016162605_exchange_escrow_market.sql)을 기존 선물·창고·지갑 스키마가 있는 DB에 증분 적용합니다. 테이블 초기화나 기존 낚시 RPC 재정의는 하지 않습니다. 원격 적용은 수행하지 않았습니다. [DB 관리 절차](database-management.md)를 따릅니다.

검증 명령:

```powershell
npm.cmd test -- tests/exchange-sql.test.ts tests/exchange-ui.test.tsx tests/gifts.test.tsx tests/notifications-page.test.tsx
npm.cmd run db:context
npm.cmd run build
```

PGlite로 골드·미끼·개체 물물교환, 등록 보관, 판매/직접 수령 차단, 취소 반환, 중복 요청, 잔액·수량·활성 글 한도, 다른 계정 접근, 우편 보유 한도와 기존 친구 선물 호환을 검사합니다. PGlite의 요청은 직렬 실행이므로 실제 다중 연결 동시 경합 검증을 대체하지 않습니다. 전체 `db:verify`는 기존 SQL 39~62번의 동결 manifest 불일치로 중단되는 별도 문제가 있습니다.
