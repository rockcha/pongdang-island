# 생산소 운영 원칙

## 미끼 생산소

미끼 생산소는 연료 생산소와 별도의 보유 시설·작업 원장을 사용한다. 같은 시설을 여러 곳 구매할 수 있고 보유 수에는 제한을 두지 않는다. 연료·미끼 생산소를 합쳐 완료 시각이 아직 지나지 않은 시설은 동시에 최대 4곳까지 가동한다. 완료·만료된 시설은 가동 자리를 차지하지 않지만, 해당 시설을 다시 쓰려면 먼저 생산물을 수령하거나 만료 후 정리해야 한다. 자동 재생산은 하지 않는다.

가동 시 연료를 한 번 차감하고 생산 미끼 ID·생산량·완료·만료 시각을 저장한다. 이후 카탈로그 변경은 진행 중인 생산물에 소급하지 않는다. 완료 후 보관시간 안에 수령하면 지갑의 해당 미끼 재고에 더하며, 만료된 생산물은 지급 없이 정리한다. 추가 연료를 내는 만료 복구는 제공하지 않는다. 완료 알림과 시설 재판매는 이번 미끼 생산소 범위에 포함하지 않는다.

구매·생산 요청은 사용자 지갑을 먼저 잠가 동시 요청의 연료 중복 차감과 가동 제한 초과를 막는다. 응답이 불확실하면 같은 요청 ID로 재시도하고, 다른 작업으로 덮어쓰지 않는다. 카탈로그 수치는 원본에서 관리하며 DB 재생·보안·카탈로그 검증과 미끼 생산소 SQL/UI 테스트로 확인한다. 로컬 구현과 검증은 원격 배포 완료의 증거가 아니다.

## 연료 생산소

연료 생산소의 총 보유 수는 제한하지 않는다. 한 번의 묶음 구매 수량은 서버에서 검증하며, 지갑 잠금·잔액 검사·요청 영수증을 유지한다. 동시 가동 제한은 연료·미끼 생산소를 합산하며 보유 수에는 적용하지 않는다.

연료 생산소 상점에서 같은 종류도 여러 곳 구매하고, 보관함의 자원을 선택해 연료를 생산한다. 구매 수량의 합계를 한 번에 결제하며 각 시설은 별도의 보유 ID와 생산 시각을 가진다. 상점은 상품별 보유 수를, 생산소는 보유한 개별 시설을 표시한다. 쓰레기 재활용과 어유 정제는 같은 연료를 생산하며 재료 종류만 다르다. 재료 효율과 생산·보관 시간을 비교하는 구조이며, 시설별 수치는 카탈로그 원본에서 관리한다.

가동·수령·폐기와 일괄 처리에는 상품 ID 대신 보유 시설 ID를 사용한다. 기존의 단일 시설 요청과 작업 영수증은 유지하되, 같은 상품이 여러 곳이면 상품 ID만으로 가동할 곳을 임의 선택하지 않는다. 기존 복합 키를 바꿀 때는 보유 행과 진행 중인 생산 스냅샷을 보존한다. 일괄 처리 중 매 시설마다 전체 목록을 만들지 않고 마지막에 한 번만 반환한다.

상점은 현재 카테고리에서 이름을 검색하고 선택한 기준으로 정렬한다. 각 기준은 정해진 정렬 방향을 사용한다. 구매 수량과 비용은 서버에서 별도로 검증한다.

어유 정제의 초기 균형은 물고기 한 마리를 쓰레기 여러 개에 대응시키는 재료 효율을 우선하고, 생산·보관 시간을 추가 조정하는 방식으로 잡았다. 단순히 마릿수만 비교하지 않는다. 정수 수량 때문에 초보 시설은 회차 생산량을 늘려 조정할 수 있으며, 대량 시설도 짧은 수령 기한과 처리량 사이의 선택이 남아야 한다. 두 종류의 자원을 서로 대체해서 소비하거나 다른 연료를 지급하지 않는다.

- 재료는 시설의 종류와 일치해야 하며, 어항 배치·판매·선물 보관 중인 개체는 제외한다. 서로 다른 종을 섞을 수 있다. 저렴한 재료 채우기는 사용자가 눌렀을 때만 실행한다.
- 가동 시 재료를 즉시 소비하며 취소하지 않는다. 완료 후 보관시간이 지나면 생산물을 수령할 수 없고, 정리한 뒤 다시 가동한다. 보관시간은 접속 여부와 무관하게 완료 시점부터 계산한다.
- 서버가 시작·완료·만료 시각과 해당 회차의 생산량을 저장한다. 카탈로그 변경으로 진행 중인 생산의 시간이나 수량을 바꾸지 않는다. UI 시계는 서버 시각에 보정하며 복귀·재연결 때 갱신한다. 상태 계산에는 주기적인 DB 작업이 필요하지 않다.
- 완료 알림은 생산 회차마다 한 번만 소식 알림함에 남기며 생산소로 연결한다. 접속 중에는 서버가 준 다음 완료 시각에 확인하고, 미접속 중에는 Cron이 매분 확인한다. 수령·정리한 회차와 보관 기한이 지난 생산물은 새로 알리지 않는다. 배포 시 Cron 등록도 확인하며, 접속 시 누락된 알림을 보충한다.
- 소비한 개체는 획득 이력을 유지한다. 기존 보관함·판매·선물 함수의 이용 가능 조건과 호환되도록 기존 판매/퇴역 시각과 별도의 소비 시각을 함께 기록하며, 판매 대금이나 판매 거래는 생성하지 않는다. 두 시각을 임의로 초기화하면 소비한 재료가 복원되므로 금지한다.
- 구매·가동·수령·정리는 서버 RPC에서 권한·소유권·수량을 검증한다. 지갑, 보유 시설, 개체 순서로 잠그고 개체 ID 순서를 고정한다. 요청 식별자를 재사용해 응답 유실 후 재시도가 중복 구매·소비·지급으로 이어지지 않게 한다. 작업 원장을 임의로 삭제하지 않는다.
- 일괄 처리는 현재 카테고리의 해당 상태 시설을 대상으로 하며 실행 전에 확인한다. 일괄 가동은 저렴한 시설 순서로 재료를 배분하되 같은 재고를 중복 계산하지 않고, 판매가가 낮은 종부터 사용한다. 특급·신화가 실제 소모 목록에 포함되면 명시적인 추가 확인을 요구한다. 서버는 확인한 종과 수량만 사용하며 더 비싼 종으로 대체하지 않는다. 재료 부족이나 상태 변경으로 어느 한 곳이 실패하면 전체 작업을 취소한다. 상위 작업과 개별 처리 영수증은 같은 트랜잭션에 기록해 일괄 재시도의 중복 지급을 막는다.

카탈로그·구조 변경은 [DB 관리 절차](database-management.md)를 따른다. `tests/production-sql.test.ts`는 소유권·중복 요청·재료 소비·수령·만료를, `tests/production-page.test.tsx`는 구매와 재료 선택 흐름을 검증한다. 브라우저 미리보기는 RPC 응답을 모의하므로 원격 적용 여부의 근거로 사용하지 않는다. 실제 적용 후에는 대상 프로젝트의 관련 카탈로그·RPC 권한·RLS를 별도로 조회한다.

## 상태 연출

생산 중·수령 대기는 투명 배경의 8프레임 스프라이트를 사용한다. 가동 대기는 위로 떠오르는 Zzz, 만료는 기울어지는 모래시계와 흩날리는 먼지로 표시한다. 상태 설명은 텍스트로도 제공하고, 움직임 줄이기 설정에서는 애니메이션을 멈춘다. 생성 프롬프트와 원본은 `assets/references/production-status/manifest.json`을 출발점으로 찾는다. 프레임을 준비할 때는 시퀀스 전체에 같은 축척을 적용하고 고정된 몸체의 중심·바닥을 정렬한다. 불꽃·연기의 움직임을 프레임마다 따로 확대하지 않는다. 경계 여백을 검사하고, 움직임 줄이기 설정에서는 첫 프레임을 표시한다.
