# 바다 상인의 의뢰

혼합 주문은 수집 부담을 줄이기 위해 각 종류를 한 개씩 요구하고 일반 등급 한 종류에만 추가 한 개를 허용한다. 매일 주문 구성은 확률로 개수를 정하지 않고 수량 패턴마다 정해진 주문 수를 채운다. 종류 수가 같은 주문도 요구 수량에 따라 추가 보상을 다르게 계산한다.

이 콘텐츠는 보관함 개체를 소모하는 서버 공통 선착순 납품처다. 정해진 총액으로 매입하며 서버 공통 주문 수로 공급량을 제한한다. 개인별 납품 횟수 제한은 두지 않는다. 수량 패턴을 먼저 정하고 주문 전체의 최고 등급을 한 번만 추첨한 뒤 물고기·쓰레기·장식물을 섞는다. 최고 등급이 희귀이면 단일 수량 슬롯 중 희귀 종류 수를 균등 추첨한다. 특급·신화는 주문당 한 종류만 포함하고 나머지는 일반으로 채운다. 슬롯마다 등급을 따로 뽑아 종류가 많을수록 신화가 흔해지는 구조로 바꾸지 않는다. 해역은 납품 조건이 아니므로 카드에 표시하지 않는다. 구체적인 수량·지급액·종류 비중은 최신 merchant migration과 테스트를 기준으로 한다.

주문은 한국 날짜를 기준으로 첫 조회 시 트랜잭션 하나에서 생성한다. 같은 날짜의 생성은 advisory lock과 날짜 키로 직렬화하며, 조회만으로 미완성된 주문판이 노출되면 안 된다. 별도 브라우저 타이머나 특정 사용자의 지역·보유 개체로 주문을 다시 생성하지 않는다. 규칙을 바꿀 때는 버전을 올리고 미완료 주문만 새 ID로 교체한다. 완료 주문과 지급 영수증은 보존하며, 이전 화면에서 확인하던 주문은 재료를 잘못 소모하는 대신 없는 주문으로 거절해야 한다. 서버 공통 날짜별 주문판은 Supabase 프로젝트 단위다. 첫 버전에서는 별도 게임 서버/샤드 식별자를 사용하지 않는다.

납품은 전체 재료가 준비된 경우에만 완료한다. 어항에 배치된 개체, 판매한 개체, 선물·거래 예약 중인 개체는 사용할 수 없다. 보관함으로 받은 개체는 납품할 수 있으나 납품이 도감을 해금하거나 포획 기록을 만들지는 않는다. 총 지급액은 생성 시점의 일반 판매가에 수량 패턴과 등급 구성에 따른 추가 보상을 더한다. 특급·신화의 혼합 주문은 해당 슬롯을 일반으로 본 기본 보상에 등급별 가산액을 더한다. 카드·확인창·영수증은 모두 실제 총 지급액을 사용하며 확인창에서 판매가와 추가 보상을 구분한다. 완료된 주문과 지급 영수증은 규칙 전환 시에도 유지한다. 카탈로그 가격을 바꿔도 이미 생성된 주문 보상은 유지한다.

지갑 → 주문 → 개체 ID 순으로 잠근 뒤 수량·마감·골드 한도를 재검사한다. 판매 표시, 골드 지급, 주문 완료, 납품 영수증은 같은 트랜잭션에서 처리한다. 일시적인 통신 실패 때는 계정별로 저장한 operation ID를 재사용한다. 재시도는 다음 날짜에도 기존 영수증을 반환해야 하며 다시 재료를 소모하거나 보상을 지급하면 안 된다. 날짜가 지난 미완료 주문은 납품할 수 없다.

원본 테이블과 생성 함수는 private이며 클라이언트의 직접 읽기·쓰기를 허용하지 않는다. 공개 RPC는 인증된 플레이어의 보관함 수량과 주문 완료 여부만 반환하며 납품자의 계정 ID는 공개하지 않는다. 완료 카드에는 납품 당시 공개 이름과 선택 입력한 한마디를 보존하고, 아바타는 현재 공개 프로필을 표시한다. 프로필 변경 때 이전 이미지 파일을 삭제하므로 당시 경로를 영구 이미지로 취급하지 않는다. 한마디는 원문 텍스트로 렌더링하고 지급 영수증과 함께 보존한다. 재시도에서 같은 operation ID로 문구를 바꾸면 충돌로 거절한다. 목록은 주기적으로 갱신하되 선착순 성공 여부는 납품 RPC의 결과가 최종이다.

검증은 `tests/merchant-orders-sql.test.ts`, `tests/merchant-orders-ui.test.tsx`, `npm run db:verify`, `npm run build`로 한다. 운영 중에는 날짜별 주문 완료율과 납품 영수증의 총 지급량과 일반 판매가 차이을 확인해 보상과 난이도를 조정한다. 과거 영수증이나 완료 주문을 지우면 재시도·지급 근거가 달라지므로 임의로 초기화하지 않는다.
